# Candidate: EOS guard for unclosed generated grounding tags

Prepared locally only. No GPU/tool/API invocation, production helper, deployment, cache replacement, or runtime-source modification has been performed. This candidate needs root review, an actual new DeepSeek operational review, and a concrete execution scope before use.

The one completed diagnostic reproduced the failure. It generated 13 tokens, ending in EOS 2, with an opening `<obj>` and no closing `</obj>`. The installed tokenizer maps these tags to 32000 and 32001, neither special; the closing ID was not generated. Thus `skip_special_tokens=True` did not delete a closing tag. The original converter asserted that an end delimiter must exist. This was early EOS rather than the 300-token limit. No clinical finding or target reference is needed to establish this format failure.

`local_assets/r49_phrase_grounding_eos_guard_candidate.py` proposes an explicit generation-policy amendment. Its processor inspects only token IDs generated after the actual input prompt length. It counts unmatched object and box delimiters independently: `<obj>` 32000, `</obj>` 32001, `<box>` 32202, `</box>` 32203. If either depth is positive, only EOS 2 is masked to negative infinity for that batch row. All other scores and the input scores tensor remain unchanged. Balanced or ordinary-text suffixes allow EOS unchanged. This is not a complete grammar validator: orphan, crossed, malformed, or otherwise unsupported output remains subject to the original strict parser.

The candidate does not append a token, demand a bounding box, truncate or delete text, add a clinical prompt, retry a model call, alter sampling or beam settings, change model/precision/quantization, change `max_new_tokens=300`, or convert an error to `completed_no_finding`. It delegates the original bound `generate`, adding a logits processor while preserving existing processors. The model's actual output is still parsed by the unmodified tool. If output remains malformed, reaches its limit unclosed, or another failure occurs, execution must stop. Masking EOS can prolong generation and change subsequent words, findings, or boxes; those are real method changes and may improve or harm answers. Correct formatting does not establish clinical correctness.

Recommended scope if accepted: activate this policy after the 168 committed-question boundary for all subsequent new physical MAIRA invocations in the authorized three-dataset stream. Preserve all existing healthy cache results and saved selections under their original policy, identifying such cache reuse explicitly. This is more consistent than secretly changing only the failing question. It also means the final run contains an openly disclosed policy boundary and cannot be described as a fully unchanged executor or a causal test of Skill learning alone. The known question-169 failed selection gets at most one newly reviewed guarded production attempt; the original failed cache and all 168 predictions, feedback, five Skill windows, and existing recovery overlays remain intact. New failures get no automatic second retry.

Any operational implementation must use an explicit guarded cache namespace and policy metadata so original and amended generation results cannot be silently conflated. It must record actual mapping/configuration, activation boundary, whether a selection used an old healthy cache or a new guarded call, EOS-masking step counts and unmatched depths, original/raw results, time, and all prior failures. The diagnostic result must never substitute for the production result. This file is a proposed scope, not a production execution authorization or a claim that all causes have been fixed.
