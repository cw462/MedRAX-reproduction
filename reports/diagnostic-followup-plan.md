# Frozen follow-up plan: output-cap diagnosis

Prepared while the initial 50-question development run is executing, before its reference-answer scoring. This plan targets a mechanical observation: some first-phase responses reach the 512-token output cap, and one truncated response has an invalid-tool-call marker followed by a BadRequestError. The precise HTTP 400 response body was not retained, so that error cause remains a hypothesis supported by the protocol path, not a confirmed server diagnosis.

After the first run completes, select the first ten questions in its already frozen input order for which either arm reports `model_output_truncated`. Do not select by answer correctness, improvement, diagnosis or reference labels. Rerun both arms for those questions with a 1024-token output cap, keeping question/image bytes, model ID, temperature, prompts, tool set and invocation limits unchanged. Record original run/manifest/result hashes, selection, new configuration, every request and all failures. Keep the initial 512-token results unchanged.

This is a targeted development follow-up, not an independent held-out evaluation or an estimate for all ChestAgentBench questions. Sampling variation and repeated API requests are not fully controlled, so accuracy changes cannot establish a clean causal effect of the cap. The primary observations are finish reasons, malformed-tool-call frequency, valid final answers, requests and token costs. A malformed result must not be repaired by inventing a tool message, observation or answer.

The original shared CNY 100 ledger remains authoritative. The follow-up uses two 512-token reservation blocks before one 1024-token request, conserving the original ledger policy and all prior expenditure. Both blocks must be reserved before sending. The combined worst-case reservation deliberately reserves the input-cost allowance twice and is conservative; the logical input bound remains 128000 tokens. Actual complete usage is split without double-counting input. Unknown charges retain both full reservations. A failed second reservation causes no API request and conservatively retains the first reservation. Total-bound violations must persistently stop future calls. Ledger entries are reservation blocks, not API request counts.

Protocol-check helpers are implemented and tested separately; they are **not** enabled in the cap-only comparison, because adding them would change two factors at once. A subsequent protocol-fix experiment, if warranted, must have its own configuration and report.
