## Finding 1: the frozen retriever is not question-specific

`FrozenPool.search` tokenises only the boundary entry's coarse `features` tags.
On the 29 frozen validation questions under R3:

```
rank 1: 29 questions -> 7 distinct memories
all ranks: 87 slots -> 18 distinct memories
distinct injected blocks: 7 of 29 questions
largest identical block group: 12
```

Twelve different questions received byte-identical memory blocks. So the R3 gain
is closer to a global prompt perturbation than to per-question retrieval, which
also explains why R2 (rule summary) measured the same as R0.

R5 fixes this by joining `record.source_question_id` to the frozen training
inputs file and ranking on real question text. Measured, frozen guards intact:

```
frozen : 7 distinct rendered blocks / 29   (largest group 12)
text   : 28 distinct rendered blocks / 29  (largest group 2)
identical between retrievers: 0/29
```

## Finding 2: MAIRA-2 was blocked by dtype, not by transformers

`XRayPhraseGroundingTool` calls `from_pretrained()` without `torch_dtype`, so the
7B model loads in fp32 (~31 GB) and cannot fit a 24 GB RTX 3090 at all. In bf16 it
needs 12.8 GiB and loads in ~7 s; grounding calls take 0.7–2.4 s.

Two upstream defects surfaced while wiring it:

1. `convert_output_to_plaintext_or_grounded_sequence` asserts when the model emits
   no `<phrase>` span. A legitimate "nothing to ground" therefore arrives as
   `analysis_status=failed`. The tool already contains a `completed_no_finding`
   branch that this exception makes unreachable.
2. `pred_bboxes` can be `None`; the upstream `_run` skips those entries and any
   reimplementation must too.

After both fixes: 5/5 real groundings on subset images returned boxes, 0 failures.

## Finding 3: the pool is redundant by content, so R7 is diversity not capacity

Only 18 of the 60 records are ever retrieved, so a size cap would remove almost
nothing. Clustering records by their exposed structural signature (feature tags,
tool names, observation shapes, outcome) shows the redundancy:

```
signature clusters at Jaccard 0.85: 17 for 60 records
cluster sizes: {1: 10, 2: 1, 3: 3, 7: 1, 12: 1, 20: 1}
largest cluster: 20 records
```

Applied after retrieval, the diversity filter removes near-duplicates from a block:

```
on the frozen R3 blocks:        11 of 87 slots removed, 9/29 blocks shrink
on the R5 text-retriever blocks: 32 of 87 slots removed, 25/29 blocks shrink,
                                 29/29 blocks still non-empty
```

So the two effects are related: the text retriever is question-specific in
*ranking* but pulls clusters of near-identical memories, and R7 removes 37% of
that block content. Whether a smaller, more diverse block is *better* is exactly
what the next validation run has to measure - the filter is implemented and safe,
not yet shown to help.
