## How the branches behaved

| branch | changed the letter | made ≥1 tool call | its reasoning mentions the block |
|---|---:|---:|---:|
| P1 | 16/54 (0.296) | 52/54 (0.963) | — |
| PB | 3/59 (0.051) | 28/59 (0.475) | 48/59 (0.814) |
| PC | 0/57 (0.000) | 18/57 (0.316) | 47/57 (0.825) |

The memory branches do read the block — their reasoning names it in about 82% of cases —
and then mostly decide it does not apply. Representative reasoning from the records:
"The operating experience provided (SKILL S017) is about distinguishing giant bulla from
pneumothorax in COPD patients ... this case does not involve COPD or bullous emphysema"
(10569/PC), and "the grounding tool is wrong here, I keep my reading" (11624/PC). That is
not a failure to engage; it is the model rejecting the advice.

The one branch that does change answers is P1, the branch with **no memory at all**.
Asking the model to take one more targeted look at its answer makes it abandon correct
answers: 12 harms against 2 corrections, worse in every question type.

## The two design conclusions

1. **The gate works but has nothing to gate.** GB blocked every harm PB produced (3/3).
   It cannot be evaluated on corrections because PB produced none. A gate is only as
   useful as the candidates it is given.
2. **"Look again" is not a neutral control — it is harmful.** P1's net is −10. Any design
   that adds a verification pass must expect the pass itself to cost accuracy; the plan
   treated P1 as "the value of one more re-check", and that value is negative here.

## Why the memory produced no candidates

The post-hoc blocks are the *same* representations the old B/C arms used: B = tool
trajectories from other training cases (no clinical content), C = reusable skill cards
(trigger/need/do). Both were built to be injected *before* the first observation. Used
after the fact, they contain nothing that contradicts the current answer: they say which
tools succeeded elsewhere, or which attributes are generally worth checking. The model
checks one or two of those attributes, sees nothing decisive, and keeps its answer.

For a candidate to exist, one of two things has to change:

* the memory must carry a **specific alternative claim** about this case ("a case with
  this feature had X; if this image shows X, the answer is not Y"), or
* the candidate must be generated by **enumerating option-vs-observation mismatches**
  (the plan's `proposed_edit_set`), with memory only prioritising which mismatch to test.

Neither is in this run. That is the next experiment, not a threshold change.

## A baseline fact that changes how to read the old numbers

P0 differs from the S2 A arm on **13 of 59 questions (22%)** — same model, prompt, tools
and questions. The historical B/C corrections and harms therefore cannot be used as the
baseline for a new run; every comparison in this report is against this run's own P0.
It also means the earlier "A 65%, B 63%, C 55%" split is within the run-to-run spread of
a single arm.

## Decision

Per the plan's own rule, a gate that blocks harm is only accepted if it also keeps
corrections. With 0 corrections and 3 blocked harms, this run **does not support fixing
the scheme and repeating it end to end**. The next step is the candidate-stage redesign
above, on a smaller diagnostic set, before any further 60-question run.
